# 기능 계획 도구 (Feature Planner)

## 목적
다음과 같은 구조화된 단계별 계획 생성:
- 각 단계는 완전하고 실행 가능한 기능 제공
- 품질 게이트는 다음 단계로 진행하기 전 검증 강제
- 작업 시작 전 사용자가 계획 승인
- 마크다운 체크박스로 진행 상황 추적
- 각 단계는 최대 1-4시간

## 계획 워크플로우

### 1단계: 요구사항 분석
1. 코드베이스 아키텍처를 이해하기 위해 관련 파일 읽기
2. 의존성 및 통합 지점 식별
3. 복잡성과 위험 평가
4. 적절한 범위 결정 (소/중/대)

### 2단계: TDD 통합을 통한 단계별 분해
기능을 3-7단계로 분해하며, 각 단계는:
- **테스트 우선**: 구현 전에 테스트 작성
- 작동하고 테스트 가능한 기능 제공
- 최대 1-4시간 소요
- Red-Green-Refactor 사이클 준수
- 측정 가능한 테스트 커버리지 요구사항
- 독립적으로 롤백 가능
- 명확한 성공 기준

**단계 구조**:
- 단계 이름: 명확한 산출물
- 목표: 이 단계가 생산하는 작동 기능
- **테스트 전략**: 테스트 유형, 커버리지 목표, 테스트 시나리오
- 작업 (TDD 워크플로우 순서):
  1. **RED 작업**: 먼저 실패하는 테스트 작성
  2. **GREEN 작업**: 테스트를 통과하는 최소한의 코드 구현
  3. **REFACTOR 작업**: 테스트가 통과하는 상태를 유지하며 코드 품질 개선
- 품질 게이트: TDD 준수 + 검증 기준
- 의존성: 시작 전에 존재해야 하는 것
- **커버리지 목표**: 이 단계에 대한 구체적인 비율 또는 체크리스트

### 3단계: 계획 문서 생성
plan-template.md를 사용하여 생성: `docs/plans/PLAN_<기능-이름>.md`

포함 사항:
- 개요 및 목표
- 근거가 있는 아키텍처 결정
- 체크박스가 있는 완전한 단계별 분해
- 품질 게이트 체크리스트
- 위험 평가 표
- 단계별 롤백 전략
- 진행 상황 추적 섹션
- 노트 및 학습 영역

### 4단계: 사용자 승인
**중요**: 진행하기 전에 AskUserQuestion을 사용하여 명시적인 승인 받기.

질문:
- "이 단계별 분해가 프로젝트에 적합한가요?"
- "제안된 접근 방식에 대한 우려사항이 있나요?"
- "계획 문서를 작성해도 될까요?"

사용자가 승인을 확인한 후에만 계획 문서를 생성합니다.

### 5단계: 문서 생성
1. `docs/plans/` 디렉토리가 없으면 생성
2. 모든 체크박스가 체크되지 않은 상태로 계획 문서 생성
3. 헤더에 품질 게이트에 대한 명확한 지침 추가
4. 사용자에게 계획 위치 및 다음 단계 안내

## 품질 게이트 기준

다음 단계로 진행하기 전에 각 단계는 다음 항목을 검증해야 합니다:

**빌드 및 컴파일**:
- [ ] 프로젝트가 오류 없이 빌드/컴파일됨
- [ ] 구문 오류 없음

**테스트 주도 개발 (TDD)**:
- [ ] 프로덕션 코드 전에 테스트 작성
- [ ] Red-Green-Refactor 사이클 준수
- [ ] 단위 테스트: 비즈니스 로직 ≥80% 커버리지
- [ ] 통합 테스트: 중요 사용자 플로우 검증
- [ ] 테스트 스위트가 허용 가능한 시간 내에 실행 (<5분)

**테스팅**:
- [ ] 모든 기존 테스트 통과
- [ ] 새 기능에 대한 새 테스트 추가
- [ ] 테스트 커버리지 유지 또는 개선

**코드 품질**:
- [ ] 린팅이 오류 없이 통과
- [ ] 타입 체크 통과 (해당하는 경우)
- [ ] 코드 포맷팅 일관성

**기능성**:
- [ ] 수동 테스트를 통해 기능 작동 확인
- [ ] 기존 기능에 리그레션 없음
- [ ] 엣지 케이스 테스트됨

**보안 및 성능**:
- [ ] 새로운 보안 취약점 없음
- [ ] 성능 저하 없음
- [ ] 리소스 사용량 허용 가능

**문서화**:
- [ ] 코드 주석 업데이트
- [ ] 문서가 변경 사항 반영

## 진행 상황 추적 프로토콜

계획 문서 헤더에 추가:

```markdown
**중요 지침**: 각 단계 완료 후:
1. ✅ 완료된 작업 체크박스 체크
2. 🧪 모든 품질 게이트 검증 명령 실행
3. ⚠️ 모든 품질 게이트 항목이 통과했는지 확인
4. 📅 "최종 업데이트" 날짜 업데이트
5. 📝 노트 섹션에 학습 내용 문서화
6. ➡️ 그 후에만 다음 단계로 진행

⛔ 품질 게이트를 건너뛰거나 실패한 체크로 진행하지 마세요
```

## 단계 크기 지침

**소규모 범위** (2-3단계, 총 3-6시간):
- 단일 컴포넌트 또는 간단한 기능
- 최소한의 의존성
- 명확한 요구사항
- 예시: 다크 모드 토글 추가, 새 폼 컴포넌트 생성

**중규모 범위** (4-5단계, 총 8-15시간):
- 여러 컴포넌트 또는 중간 정도의 기능
- 약간의 통합 복잡성
- 데이터베이스 변경 또는 API 작업
- 예시: 사용자 인증 시스템, 검색 기능

**대규모 범위** (6-7단계, 총 15-25시간):
- 여러 영역에 걸친 복잡한 기능
- 상당한 아키텍처 영향
- 여러 통합
- 예시: 임베딩을 활용한 AI 기반 검색, 실시간 협업

## 위험 평가

식별 및 문서화:
- **기술적 위험**: API 변경, 성능 문제, 데이터 마이그레이션
- **의존성 위험**: 외부 라이브러리 업데이트, 서드파티 서비스 가용성
- **타임라인 위험**: 복잡성 미지수, 차단 의존성
- **품질 위험**: 테스트 커버리지 격차, 리그레션 가능성

각 위험에 대해 명시:
- 확률: 낮음/중간/높음
- 영향: 낮음/중간/높음
- 완화 전략: 구체적인 실행 단계

## 롤백 전략

각 단계에 대해 문제 발생 시 변경 사항을 되돌리는 방법을 문서화합니다.
고려 사항:
- 취소해야 할 코드 변경 사항
- 되돌릴 데이터베이스 마이그레이션 (해당하는 경우)
- 복원할 구성 변경
- 제거할 의존성

## 테스트 명세 지침

### 테스트 우선 개발 워크플로우

**각 기능 컴포넌트에 대해**:
1. **테스트 케이스 명세** (어떤 코드도 작성하기 전에)
   - 어떤 입력을 테스트할 것인가?
   - 어떤 출력이 예상되는가?
   - 어떤 엣지 케이스를 처리해야 하는가?
   - 어떤 오류 조건을 테스트해야 하는가?

2. **테스트 작성** (Red 단계)
   - 실패할 테스트 작성
   - 테스트가 올바른 이유로 실패하는지 확인
   - 테스트 실행하여 실패 확인
   - TDD 준수 추적을 위해 실패하는 테스트 커밋

3. **코드 구현** (Green 단계)
   - 테스트를 통과하는 최소한의 코드 작성
   - 테스트를 자주 실행 (2-5분마다)
   - 모든 테스트가 통과하면 멈춤
   - 테스트 이상의 추가 기능 없음

4. **리팩토링** (Blue 단계)
   - 테스트가 통과 상태를 유지하며 코드 품질 개선
   - 중복 로직 추출
   - 네이밍 및 구조 개선
   - 각 리팩토링 단계 후 테스트 실행
   - 리팩토링 완료 시 커밋

### 테스트 유형

**단위 테스트**:
- **대상**: 개별 함수, 메서드, 클래스
- **의존성**: 없음 또는 모킹/스터빙됨
- **속도**: 빠름 (테스트당 <100ms)
- **격리**: 외부 시스템으로부터 완전 격리
- **커버리지**: 비즈니스 로직 ≥80%

**통합 테스트**:
- **대상**: 컴포넌트/모듈 간 상호작용
- **의존성**: 실제 의존성 사용 가능
- **속도**: 중간 (테스트당 <1초)
- **격리**: 컴포넌트 경계 테스트
- **커버리지**: 중요 통합 지점

**엔드투엔드 (E2E) 테스트**:
- **대상**: 완전한 사용자 워크플로우
- **의존성**: 실제 또는 실제에 가까운 환경
- **속도**: 느림 (초에서 분 단위)
- **격리**: 전체 시스템 통합
- **커버리지**: 중요 사용자 여정

### 테스트 커버리지 계산

**커버리지 임계값** (프로젝트에 맞게 조정):
- **비즈니스 로직**: ≥90% (중요 코드 경로)
- **데이터 접근 계층**: ≥80% (레포지토리, DAO)
- **API/컨트롤러 계층**: ≥70% (엔드포인트)
- **UI/프레젠테이션**: 커버리지보다 통합 테스트 선호

**생태계별 커버리지 명령**:
```bash
# JavaScript/TypeScript
jest --coverage
nyc report --reporter=html

# Python
pytest --cov=src --cov-report=html
coverage report

# Java
mvn jacoco:report
gradle jacocoTestReport

# Go
go test -cover ./...
go tool cover -html=coverage.out

# .NET
dotnet test /p:CollectCoverage=true /p:CoverageReporter=html
reportgenerator -reports:coverage.xml -targetdir:coverage

# Ruby
bundle exec rspec --coverage
open coverage/index.html

# PHP
phpunit --coverage-html coverage
```

### 일반 테스트 패턴

**준비-실행-확인 (AAA) 패턴**:
```
test '동작 설명':
  // Arrange: 테스트 데이터 및 의존성 설정
  input = createTestData()

  // Act: 테스트 중인 동작 실행
  result = systemUnderTest.method(input)

  // Assert: 예상 결과 검증
  assert result == expectedOutput
```

**Given-When-Then (BDD 스타일)**:
```
test '기능이 특정 방식으로 동작해야 함':
  // Given: 초기 컨텍스트/상태
  given userIsLoggedIn()

  // When: 액션 발생
  when userClicksButton()

  // Then: 관찰 가능한 결과
  then shouldSeeConfirmation()
```

**의존성 모킹/스터빙**:
```
test '컴포넌트가 의존성을 호출해야 함':
  // 모크/스텁 생성
  mockService = createMock(ExternalService)
  component = new Component(mockService)

  // 모크 동작 구성
  when(mockService.method()).thenReturn(expectedData)

  // 실행 및 검증
  component.execute()
  verify(mockService.method()).calledOnce()
```

### 계획에서의 테스트 문서화

**각 단계에서 명시**:
1. **테스트 파일 위치**: 테스트가 작성될 정확한 경로
2. **테스트 시나리오**: 구체적인 테스트 케이스 목록
3. **예상 실패**: 테스트가 처음에 어떤 오류를 표시해야 하는가?
4. **커버리지 목표**: 이 단계의 비율
5. **모킹할 의존성**: 무엇을 모킹/스터빙해야 하는가?
6. **테스트 데이터**: 필요한 픽스처/팩토리는 무엇인가?
